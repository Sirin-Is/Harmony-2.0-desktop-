# Harmony

CRM для бухгалтера, що веде ФОП: загальні дані, доходи, податки по групах ЄП, звітність, оплати бухгалтерських послуг, налаштування. Дані зберігаються в хмарі (Supabase), доступні з будь-якого пристрою.

## Запуск (у браузері)

Просто відкрийте `index.html` подвійним кліком. Термінал і PowerShell не потрібні. Потрібен лише інтернет — застосунок завантажує й зберігає всі дані через Supabase (детальніше нижче).

Якщо кнопки не реагують на клік або дані не завантажуються — натисніть **F12**, відкрийте вкладку **Console**, перезавантажте сторінку і подивіться на червоний текст помилки. Статус з'єднання видно і в самому застосунку — внизу лівого меню («⏳ Завантаження…» / «✓ Збережено в Supabase» / «⚠ Немає з'єднання»).

## Структура

```
index.html     розмітка, підключення стилів і app.js
styles.css      основні стилі (сайдбар, таблиці, модалка, форми, індикатор синхронізації)
matrix.css       стилі для «липких» колонок ПІБ/Борг/Ліміту в «Оплатах» і «Доходах»
app.js            увесь застосунок: дані, логіка, рендер, обробники подій, шар Supabase
main.js            точка входу Electron (десктоп-збірка, Крок 3 нижче)
package.json        конфігурація Electron + electron-builder
```

## Крок 1-2: База даних (Supabase)

Застосунок зберігає всю базу як **один рядок JSONB** у таблиці `app_state` — це найнижчий ризик міграції: уся наявна логіка (рендер, розрахунки) не змінилась узагалі, змінився лише спосіб завантаження/збереження `db`.

**Таблицю й політики доступу я вже створив і перевірив напряму у вашому проєкті `Project Harmony`** (`ldicshjvdxdfilucflkd`) через Supabase MCP — нічого додатково запускати не треба. SQL нижче — для довідки/відновлення, якщо колись знадобиться пересоздати таблицю на іншому проєкті:

```sql
create table if not exists app_state (
  id text primary key,
  data jsonb not null,
  updated_at timestamptz not null default now()
);

alter table app_state enable row level security;

create policy "Allow public read" on app_state
  for select using (true);
create policy "Allow public insert" on app_state
  for insert with check (true);
create policy "Allow public update" on app_state
  for update using (true);
```

Ключ `SUPABASE_URL`/`SUPABASE_KEY` прописані прямо у верхній частині `app.js` (константи `SUPABASE_URL`/`SUPABASE_KEY`). Це **publishable**-ключ — він і призначений для клієнтського коду, це не секрет на кшталт `service_role`.

### ⚠️ Важливо про безпеку

Політики RLS вище дозволяють читати й писати рядок `app_state` **будь-кому, хто знає URL і цей ключ** — а publishable-ключ у будь-якому разі видно кожному, хто відкриє `app.js` чи погляне у вкладку Network браузера. Це означає: дані всіх ваших клієнтів (ПІБ, доходи, суми, дедлайни) технічно доступні будь-кому, хто отримає файл застосунку. Для одного бухгалтера, що просто хоче синхронізацію між своїми пристроями, це прийнятний компроміс — але:
- **не викладайте білд застосунку у відкритий доступ** (публічний сайт, публічний реліз);
- якщо колись знадобиться доступ кільком людям з розділенням прав — потрібна справжня автентифікація (Supabase Auth) замість відкритих RLS-політик; це вже інша, більша задача — скажіть, якщо актуально.

### Технічні деталі шару збереження

- Завантаження — один `GET` при старті (`boot()`), поки він триває — показується оверлей завантаження.
- Збереження — **дебаунс 800мс**: швидкі послідовні зміни (введення тексту) збираються в один запит, а не шлють запит на кожне натискання клавіші.
- При закритті вкладки з незбереженими змінами — `beforeunload` примусово надсилає `fetch(..., {keepalive:true})`, щоб запит встиг дійти навіть під час закриття сторінки.
- Якщо мережі немає — застосунок не «падає»: показує зрозуміле повідомлення, працює далі з порожньою/останньою відомою базою в пам'яті для поточного сеансу, і намагається зберегти знову при наступній зміні чи закритті вкладки.
- **Я не можу протестувати цю інтеграцію з вашого браузера** (мережа мого середовища не бачить ваш Wi-Fi/браузер) — але я перевірив реальний проєкт напряму через підключений Supabase MCP: створив таблицю, вставив тестовий рядок з точнісінько такою структурою JSON, яку шле застосунок, і переконався, що вона зберігається й читається коректно. Сам виклик `fetch()` з `app.js` (заголовки, тіло запиту, `on_conflict=id`) перевірений окремим тестом, що повторює точний формат запитів Supabase REST API. Коли відкриєте застосунок у себе — перевірте індикатор синхронізації й вкладку Network у F12 на всяк випадок.

## Крок 3: Десктоп-застосунок (.exe для Windows)

```powershell
npm install
npm run start   # тестовий запуск перед збіркою
npm run dist     # збирає .exe у папку dist/ (інсталятор NSIS + portable-версія)
```

`npm run dist` створює у `dist/`:
- `Harmony Setup <версія>.exe` — звичайний інсталятор (можна обрати папку встановлення, створює ярлик на робочому столі);
- `Harmony <версія>.exe` (portable) — не потребує встановлення, просто запускається.

Якщо збираєте НЕ на Windows (Mac/Linux) під Windows-ціль — `electron-builder` може попросити Wine; найпростіше — збирати прямо на Windows-машині, як у вас зараз.

Electron-вікно (`main.js`) відкриває той самий `index.html` без жодних змін у самому застосунку — рядок меню (File/Edit/View) прибрано для чистішого вигляду окремої програми. Мережеві виклики до Supabase (`fetch`) працюють з Electron так само, як у браузері.

## Розділи

- **Огляд** — стартова сторінка. Горизонтальні рядки по кожному розділу (Загальні дані, Доходи, Податки, Звітність, Оплати) із зауваженнями, на що варто звернути увагу просто зараз. Показує до 5 ПІБ, далі — «та інші (N)». Клік на ПІБ переносить у відповідний розділ, до потрібної групи/періоду/кварталу, і на 2.5 секунди підсвічує рядок цього ФОП. Зауваження нічого не приховують за давністю — прострочене й досі не закрите лишається видимим, доки його не закриють:
  - **Загальні дані** — КЕП спливає менш ніж за 3 дні.
  - **Доходи** — залишок ліміту менший, ніж 3 середньомісячних доходи з початку року.
  - **Податки** та **Звітність** — до дедлайну ≤ 5 днів, а сплати/подання ще не було (перевіряються всі періоди року, а не лише поточний).
  - **Оплати** — до кінця місяця ≤ 5 днів, а оплата послуг за цей місяць не закрита.
- **Загальні дані** (колишній «Огляд») — таблиця всіх активних ФОП з повним ПІБ (єдине місце, де ім'я не скорочується), кастомні колонки, перетягування рядків, кількість найманих працівників.
- **Доходи** — вкладки «1-2 група» / «3 група». Дохід вводиться помісячно; для 3 групи автоматично рахуються кумулятивні колонки (I квартал / Півріччя / 9 місяців / Рік). «Залишок ліміту» = ліміт групи (з «Налаштувань») мінус накопичений дохід з початку року.
- **Податки** — вкладки «1-2 група» / «3 група» (для 1 і 2 групи дедлайни завжди однакові, тому вони об'єднані) і період. Дедлайн підставляється автоматично з «Налаштувань» (позначений пунктирною рамкою); якщо ввести свою дату для конкретного ФОП — вона матиме пріоритет. Лічильник «Днів до дедлайну» рахується від сьогодні, доки податок не сплачено — після заповнення дати сплати значення **заморожується** назавжди на різниці «дедлайн мінус дата сплати».
- **Звітність** — так само вкладки «1-2 група» / «3 група»: 1-2 групи подають звіт раз на рік, 3 група — щоквартально (ті самі періоди, що й у «Податках»). Дедлайни теж підставляються з «Налаштувань».
- **Оплати** — вкладки по кварталах (I–IV), у кожній видно лише 3 місяці, тому горизонтальна прокрутка не потрібна. «Загальний борг» завжди показує суму за весь рік, незалежно від обраного кварталу.
- **Неактивні** — приховані ФОП; дані не видаляються, можна активувати назад.
- **Налаштування** — розмір МЗП на рік і дедлайни:
  - Єдиний податок + Військовий збір, 1-2 групи — **один спільний** щомісячний дедлайн (вони завжди збігаються), у двох рядках по 6 місяців, щоб влізти на екран без прокрутки.
  - Єдиний податок + Військовий збір, 3 група — один спільний поквартальний дедлайн.
  - ЄСВ — поквартальний дедлайн, спільний для всіх трьох груп.
  - Звітність — річний дедлайн для 1-2 груп, поквартальний для 3 групи.

  Ліміт доходу (167 / 834 / 1167 МЗП для груп 1/2/3) рахується від значення МЗП автоматично — змінили МЗП тут, і ліміт одразу оновився і в формі ФОП, і в «Доходах».

## Інші деталі

- **Видалити / приховати ФОП** — тепер лише з форми редагування ФОП («небезпечна зона» внизу форми), а не окремими кнопками в таблиці — важче натиснути випадково.
- **Скорочення ПІБ** — усюди, крім «Загальні дані», ім'я показується скорочено: «Прізвище І.П.». Якщо серед активних чи неактивних ФОП є ще хтось із таким самим прізвищем, замість ініціалів показується повне ім'я без по батькові («Прізвище Ім'я»), щоб не плутати людей.
- **Суми** (в «Оплатах» і «Доходах») — порожнє поле лишається порожнім (не «-»), а введене число після виходу з поля показується з розділювачем розрядів, наприклад «1 000 000».
- Поля дат мають фіксовану ширину — введення чи очищення дати ніколи не змінює ширину колонки.

Дані зберігаються в LocalStorage браузера (ключ `fop-oblik-v1`). Кнопка «Експортувати резервну копію» в сайдбарі зберігає JSON-файл з усією базою.

Перед використанням для реального обліку перевірте актуальність дедлайнів у «Налаштуваннях» — самі дати законом не зашиті в код (вони можуть змінюватись), лише формула лімітів (167/834/1167 МЗП) фіксована.
